# Advisor hardening without application behavior changes

Migration 012 narrows function execution, moves the public rating aggregate to caller rights, rewrites auth-dependent RLS predicates for statement-level caching, splits overlapping banner/settings policies, and adds six reverse-FK indexes. The review traced every changed object from migrations 001–011 through the current anonymous, authenticated, admin, checkout, and payment callers. Signup profile creation, approved-only ratings, admin operations, public content reads, admin writes, and service-owned commerce paths retain their effective behavior; all six indexes cover nonredundant referencing-column directions.

Watch for: None; no actionable issue was found.

**Verdict**: APPROVED

## High-level view

The signup trigger remains operational after direct `EXECUTE` is removed because firing a previously created trigger does not re-check that privilege. `product_rating` remains available to both API roles and computes only approved reviews; invoker rights make review RLS authoritative without changing the aggregate.

The eleven owner/admin policy rewrites preserve their predicates while allowing `auth.uid()` and `is_admin()` to be planned once per statement. Banner consolidation keeps scheduled enabled rows public and gives administrators all-row reads and DML, while the retained settings read policy and split admin policies continue to support upsert.

All nine catalog/admin definer RPCs remain authenticated-only with in-body admin checks. The service-role checkout/payment call graph touches none of the functions whose service-role execution is revoked.

## Trigger-only signup and caller-rights rating

`handle_new_user()` remains attached to `auth.users`; PostgreSQL checked its execution privilege when migration 001 created the trigger, not when each insert fires it. Revoking direct calls therefore does not interrupt profile creation.

The replacement `product_rating(uuid)` retains the parameter, JSON shape, `count(*)`, one-decimal average, and explicit `status = 'approved'` predicate. Both versions return a null raw average for an empty set, which the application normalizes to zero. API roles retain review `SELECT` under RLS, and the approved branch exposes every input row; the explicit predicate excludes an authenticated caller’s own unapproved review and an administrator’s wider row set. The grants cover the cookie-less anonymous PDP caller and authenticated callers.

## Admin helper and definer RPC privilege chain

`is_admin()` is executable by `anon` and `authenticated`, the roles that evaluate these RLS policies. Its security-definer profile lookup avoids recursion through `profiles_owner_read`; service-role requests bypass RLS. `validate_coupon(text, integer)` runs through a cookie-bound client acting as one of those two roles, so checkout retains access.

Authenticated execution is reasserted for `reorder_categories`, `create_category`, `delete_category`, `move_category`, `reorder_featured_products`, `move_featured_product`, `admin_manage_products`, `admin_set_product_editor_state`, and `admin_duplicate_product`. Migration 012 changes no body or security mode: the six migration-010 functions and three migration-009 functions remain security definers, and each body rejects a failed `is_admin()` check before mutation. The product-editor RPC’s owner-context call to `admin_manage_products` remains valid after public/service-role revocation.

## Init-plan policy rewrites leave commerce ownership unchanged

The rewritten policies retain their command scopes, default `PUBLIC` role scope, permissive mode, and predicates. Owner comparisons on profiles, addresses, orders, wishlists, reviews, and order requests are unchanged; admin alternatives remain on the same read/delete paths; review insertion still requires its owner, `pending`, and `verified = false`; order-request insertion still requires the same user to own its parent order; and order-item reads retain the parent-order ownership/admin check.

The scalar `SELECT` wrappers are uncorrelated calls to stable request/admin helpers, changing evaluation frequency rather than authorization. They introduce no RLS cycle because `is_admin()` remains a security-definer profile lookup. No `orders` or `order_items` insert policy is recreated, preserving migration 006’s service-owned checkout boundary.

## Scheduled banners and settings upserts

The combined banner read predicate is the logical union of migration 007’s enabled/in-window public policy and the former admin `FOR ALL` policy. Public sessions see only enabled rows after an optional start and before an optional end; administrators also see disabled, future, and expired rows. Separate insert, update, and delete policies reproduce the former write checks, including both update predicates, and the authenticated invoker `reorder_site_banners` RPC remains subject to them.

`site_settings_public_read` is untouched, preserving cookie-less reads. The replacement insert and update policies provide both checks required by the current `upsert(..., { onConflict: "key" })`, with the public select policy retaining conflict-row visibility for authenticated administrators.

## Reverse-FK coverage without duplicate access paths

`order_items(product_id)` complements the existing order-led index, and `order_requests(user_id)` complements its order-led index. Existing review indexes lead with `product_id`, the banner scheduling index leads with `location`, and the wishlist primary key leads with `user_id`; none can replace the new user-, product-reference-, or product-led indexes. All six new keys therefore match real FK directions without duplicating a usable leading-key path.
