# Time-bounded, host-bound maintenance gate with signed webhook continuity

The maintenance gate blocks ordinary traffic at the middleware boundary while retaining a short-lived operator grant and an explicitly enabled Razorpay callback lane. The fixes close the prior token-replay, originless-unlock, and normalized-host gaps by signing issuance time, requiring the incoming origin, and deriving redirects and cookie binding from parsed `Host`. Razorpay continuity is closed by default and, once deliberately enabled after migration 006, passes only callback-shaped requests to a route that authenticates the exact raw body before demo or persistence behavior. No actionable source or security finding remains.

**Watch for:** **confirmed (non-blocking limitation)** no committed automated suite covers this security matrix because automated tests were prohibited; the immutable deployment requires manual validation of host/proxy semantics, expiry boundaries, all-path gating, auth continuation, cache/CSP headers, and webhook responses before cutover.

**Verdict**: APPROVED

## High-level view

The all-path Node middleware evaluates `MAINTENANCE_MODE === "1"` before static shortcuts, Supabase refresh, or route authorization. A valid operator grant resumes the existing authentication path rather than bypassing it.

The operator cookie signs a base-36 issuance timestamp and normalized incoming hostname. Server validation rejects grants older than 15 minutes or more than 30 seconds in the future; mandatory Origin validation, canonical `www` handling, and cookie binding all use the parsed incoming authority rather than Next’s normalized URL host.

Razorpay continuity requires an exact opt-in plus matching method, path, empty query, configured secret, and signature shape. Migration 006 supplies the service-role-only transitions, while the route authenticates bounded raw bytes before its demo shortcut and emits dynamic, no-store responses.

Blocked maintenance responses retain their restrictive form CSP, noindex policy, and private/CDN no-store headers. Bypassed static, application, auth-redirect, and session-refresh responses also remain no-store during the window; disabled mode keeps ordinary caching.

## Issuance time and incoming authority scope the operator grant

The cookie is `<base36-issued-at>.<base64url-hmac>`, with both timestamp and normalized hostname inside the HMAC (`middleware.ts:10-13`, `middleware.ts:63-75`). Validation rejects `issuedAt > now + 30` and `now - issuedAt > 900` before timing-safe signature comparison (`middleware.ts:89-119`), making expiry server-authoritative rather than dependent on browser `Max-Age`. The Secure, HttpOnly, SameSite=Strict `__Host-` cookie has no Domain attribute, so browser and cryptographic host boundaries align (`middleware.ts:262-282`).

`incomingHost` normalizes the incoming `Host` authority and rejects malformed values (`middleware.ts:17-46`). Unlock fails closed without both Origin and authority, then compares the URL-normalized Origin with the incoming scheme and authority before reading the secret (`middleware.ts:225-250`). The canonical branch detects `www.fasteno.in` from the same hostname and uses `nextUrl` only to retain path/query while replacing scheme, host, and port (`middleware.ts:306-313`); a copied grant fails on another hostname.

**Confirmed limitation:** source inspection cannot prove how the immutable adapter populates `Host` and `x-forwarded-proto`. Manual deployment checks must cover apex, `www`, and accepted aliases, including same-origin unlock, canonical query preservation, and cross-host replay rejection; this is an evidence requirement, not a source defect.

## Razorpay continuity is opt-in after migration 006

The exception requires exact `MAINTENANCE_ALLOW_RAZORPAY_WEBHOOK === "1"`, POST, exact webhook path, no query, a configured webhook secret, and a 64-hex signature header (`middleware.ts:213-224`). The environment template leaves it empty and requires operators to keep it unset or `0` until migration 006’s payment RPCs exist (`.env.example:61-71`); migration readiness is deliberately a deployment sequencing precondition, not a request-time database probe.

The route retains at most 256 KiB of received JSON bytes and verifies their HMAC before demo handling or parsing (`app/api/razorpay/webhook/route.ts:29-56`). Unsigned and bad-signature demo traffic therefore cannot reach success. Live events use migration 006’s service-role-only atomic RPCs, migration 010 retains that contract, and every route response is force-dynamic and no-store (`app/api/razorpay/webhook/route.ts:9`, `app/api/razorpay/webhook/route.ts:18-25`).

## The outer gate preserves auth, cache, and CSP boundaries

The Node `/:path*` matcher remains outside static and application handling (`middleware.ts:287-370`). Except for the narrowly shaped webhook lane, traffic needs a valid maintenance grant before static delivery or Supabase work; granted application requests still pass through session refresh and `/account`/`/admin` authorization. The grant opens only the maintenance boundary, not an application identity or role.

Blocked and denied responses retain private/CDN no-store, noindex, nosniff, frame denial, no-referrer, and a CSP limited to inline maintenance styles and same-origin form submission (`middleware.ts:121-211`). During maintenance, no-store is also applied to granted static responses, missing-Supabase continuations, auth redirects, and refreshed-session responses; disabled mode does not receive those overrides.
