# Callback-order-safe Razorpay amount validation

Migration 010 now checks every non-null captured amount before the paid/idempotent branch can return, resolving the previous P1 verify-first bypass. Browser verification still supplies `NULL`; same-payment retries remain idempotent, while payment-ID mismatches and cross-order reuse remain explicit reconciliation outcomes. Failed-payment stock reservation and the payment-ID write stay in one exception subtransaction, so a concurrent uniqueness loser retains neither the payment transition nor its stock decrement. No new actionable SQL or application regression was found. **Watch for:** **confirmed** validation limitation — database behavior received static review only because the provided environment has no usable PostgreSQL/Supabase/Docker runtime and the user explicitly prohibited adding tests.

**Verdict**: APPROVED

## High-level view

The authoritative amount comparison now precedes every paid-order return. A webhook arriving after browser verification must still match its non-null Razorpay amount against the local total, while the browser path remains compatible because `markOrderPaid` sends its omitted amount as `NULL`.

An order-row lock serializes callbacks for one order, the paid branch distinguishes the stored payment ID from a different one, and the partial unique payment-ID index arbitrates reuse across orders. For a previously failed order, stock reservation and payment confirmation remain atomic with the uniqueness handler.

The webhook still requires and forwards a non-negative safe-integer amount; browser verification intentionally omits it. Mismatch/conflict outcomes retain permanent reconciliation handling, TypeScript and whitespace checks pass, and the unavailable database execution is documented as a validation boundary rather than a source finding.

## Amount validation no longer depends on callback order

`confirm_razorpay_order_payment` now compares a supplied amount with the non-null integer `orders.total` immediately after locking and finding the order, before inspecting whether it is already paid. A same-ID paid row therefore returns `amount_mismatch` for a wrong non-null webhook amount and `already_paid` only for a matching amount. Browser verification calls `markOrderPaid` without options, which sends `p_captured_amount: null`; that path still reaches payment-ID validation and can confirm or idempotently recognize the payment without inventing an amount.

```
browser verify (NULL) ── paid as P
                            ├─ webhook(P, matching amount) ── already_paid
                            └─ webhook(P, wrong amount) ───── amount_mismatch

webhook(P, matching amount) ── paid
                              ├─ browser verify(P, NULL) ──── already_paid
                              └─ browser verify(Q, NULL) ──── payment_id_mismatch
```

`app/api/razorpay/webhook/route.ts` accepts `payment.amount` only as a non-negative safe integer and forwards it through `lib/orders.ts`; the browser route passes no amount. `markOrderPaid` preserves amount/identity reasons, so browser reconciliation remains HTTP 409 and the signed webhook acknowledges permanent mismatches rather than creating a retry loop.

## Payment identity arbitration keeps failed-order stock atomic

After amount validation, a paid order returns idempotent success only for its stored payment ID; a different ID returns `payment_id_mismatch`. The initial `FOR UPDATE` lock serializes same-order callbacks, so a second callback observes the first payment identity and cannot reserve stock twice.

For unpaid orders, committed cross-order reuse returns `payment_id_conflict` before mutation. Concurrent transactions that both miss that check are arbitrated by the partial unique index on non-null payment IDs, and the losing order update converts `unique_violation` into the same permanent outcome.

For a failed order, product locks, availability checks, stock decrement, and the paid transition all remain inside the exception subtransaction. A losing unique payment-ID write rolls that block back, leaving the order failed and undoing its attempted stock reservation. The moved amount check occurs before any product mutation, so it does not weaken this rollback boundary.

```
failed order A ── reserve stock ── claim payment P ── commit
failed order B ── reserve stock ── claim payment P ── unique violation
                         └──────── subtransaction rollback ── stock restored
```
