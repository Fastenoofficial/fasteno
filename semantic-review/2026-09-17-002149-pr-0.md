# Aligned modern Supabase server-secret resolution

The compatibility change now treats `SUPABASE_SECRET_KEY` as the preferred server credential and retains `SUPABASE_SERVICE_ROLE_KEY` as its legacy fallback. The service-client factory, exported capability flag, and limiter HMAC resolver all trim both candidates and make the same modern-first choice. Privileged Supabase operations continue to obtain elevated access through the server-only factory rather than reading either credential themselves.

## High-level view

`createServiceClient()` and `isServiceRoleConfigured` now agree for nonblank modern keys, whitespace-only modern values with a usable legacy fallback, and two blank candidates. The former false capability signal from whitespace-only credentials is resolved.

The limiter keeps `RATE_LIMIT_HASH_SECRET` first, then uses the same trimmed modern and legacy candidates before its existing Upstash and local fallbacks. This preserves explicit limiter-key priority while aligning credential migration behavior with privileged-client creation.

Checkout, order and guest access, shipping, Razorpay, newsletter, tracking, review verification, and administrative service operations still converge on `createServiceClient()` or `requireServiceClient()`. The factory and limiter retain `server-only` guards, the credentials remain non-`NEXT_PUBLIC_` variables, and shared configuration exposes only a Boolean capability.

No compatibility tests were added because the user prohibited new tests. TypeScript and whitespace validation pass; a production build was not run because its static-data phase can contact the configured Supabase provider.

## One normalized contract for capability and client creation

```text
Environment candidates                  Factory key   Capability   Limiter Supabase fallback
modern nonblank, legacy any              modern        true         modern
modern blank/whitespace, legacy nonblank legacy        true         legacy
both blank/whitespace                    none          false        skip to Upstash/local
```

Both candidates are trimmed before precedence is evaluated, so whitespace cannot shadow the next usable value. If both are configured, the modern secret wins in all three paths. With neither available, the factory returns `null`, the flag is false, and `requireServiceClient()` keeps mandatory privileged operations fail-closed.

## Privileged operations stay behind the server-only factory

```text
orders / guest access / shipping ─────────────┐
Razorpay / newsletter / tracking ─────────────┤
review verification / account cancellation ──┼─> createServiceClient()
admin customers / requests / service bypasses ┤       modern -> legacy
admin upload / media inventory ────────────────┘   requireServiceClient()
```

No privileged caller reads either credential directly, and none of the factory consumers is a client component. `lib/supabase/service.ts` and `lib/rate-limit.ts` import `server-only`; `.env.example` labels both credentials server-only and directs operators to configure only one.
