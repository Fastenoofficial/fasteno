# Catalog write boundaries and one-to-one Razorpay payment identity

Task 6 narrows authenticated catalog writes to draft creation and ordinary metadata editing, moves structural changes behind admin-checked RPCs, and gives each non-null Razorpay order/payment identifier one local owner. Product creation now inserts an inactive draft before applying publication state through migration 009, while payment confirmation adds mismatch/conflict outcomes and rolls back stock if a concurrent payment-ID claim loses. The privilege boundary, identifier-index race, browser compatibility, stock recapture, response classifications, and existing service/manual-order paths are coherent. One callback-ordering bug still bypasses the webhook's amount check, and these critical SQL behaviors have no executable regression coverage. **Watch for:** **confirmed** authoritative amount validation is skipped when browser verification marks the order paid first; **confirmed** ACL/RLS and two-session payment races are covered only by a manual deployment checklist.

**Verdict**: NEEDS_CHANGES

## High-level view

Every product insert explicitly uses `active = false`, with `featured = false` and `featured_order = 0` supplied by schema defaults; `admin_set_product_editor_state` then produces inactive, active, or active-and-featured state atomically. A state-RPC error leaves the first request's non-commerce draft intact and reports its ID rather than attempting a now-forbidden hard delete.

Authenticated product/category grants match the metadata editors while excluding product category/publication/order changes, product deletion, and category structural changes. Migration 001's separate admin-only product UPDATE policy remains effective, and category creation/deletion/ordering route through the converted migration-008 functions.

Those six functions retain empty search paths, schema-qualified mutable objects, explicit `is_admin()` checks, and established locks after becoming security definers. Their ACLs remove `PUBLIC`, `anon`, and `service_role`, expose EXECUTE to `authenticated`, and reject non-admin callers before mutation.

An orders-table lock closes the duplicate-preflight/index-build race, while partial unique indexes and a nested exception block make payment-ID ownership and failed-order stock recapture race-safe. The paid/idempotent branch nevertheless runs before captured-amount validation, so a webhook arriving after browser verification never compares its signed amount.

Browser verification passes `NULL`; captured webhooks require a non-negative safe integer. Semantic conflicts are permanent reconciliation outcomes, infrastructure/not-found outcomes remain retryable, and migration 010 leaves order-table/service-role privileges untouched for manual tracking and Shiprocket synchronization.

## Draft-first product creation and the catalog editor boundary

The create action inserts descriptive fields and the chosen category with `active: false`, omitting `featured` and `featured_order` (`components/admin/actions.ts:192-204`). Migration 010 grants exactly those insert columns and requires all three safe values (`supabase/migrations/010_catalog_payment_integrity.sql:315-364`). Inactive/unfeatured needs no transition, active/unfeatured invokes activation, and active/featured activates before feature membership; inactive/featured is rejected before writing.

The insert and state RPC are separate requests. If the state transaction raises, its state/activity work rolls back while the already-committed inactive/unfeatured row remains; the action returns a retained-draft error plus its ID (`components/admin/actions.ts:213-233`).

The existing-product UPDATE object and column grant contain the same descriptive, pricing, stock, media, compliance, and SEO fields, excluding `category_id`, `active`, `featured`, and `featured_order`; those fields go through `admin_set_product_editor_state` (`components/admin/actions.ts:125-188`; `supabase/migrations/010_catalog_payment_integrity.sql:336-354`). Migration 010 replaces only the product INSERT policy, leaving migration 001's `products_admin_update` policy, and drops `products_admin_delete`. Category UPDATE similarly preserves name, slug, description, image, and home visibility while excluding sort order and direct INSERT/DELETE.

## Migration-008 structural RPCs after definer conversion

Migration 010 converts category reorder/create/delete/move and featured reorder/move before withdrawing their required table privileges (`supabase/migrations/010_catalog_payment_integrity.sql:257-314`). Each migration-008 body checks `COALESCE(public.is_admin(), FALSE)` before locking or writing, uses `SET search_path = ''`, schema-qualifies persistent objects, and contains no dynamic SQL. The final ACL sequence revokes named/default application-role access, including `service_role`, and re-grants only `authenticated`; UI callers use session clients, and authenticated non-admins fail with `42501` before mutation.

## Locked identifier installation and conflict-safe stock recapture

`SHARE ROW EXCLUSIVE` is acquired before either duplicate scan and held through both unique-index builds (`supabase/migrations/010_catalog_payment_integrity.sql:20-80`). Concurrent writers cannot insert a value between preflight and index creation; existing duplicate non-null values abort the transaction with `23505`, while nulls remain allowed.

Confirmation locks the target order. Committed cross-order payment reuse is rejected up front, and the unique index arbitrates concurrent claims that both miss that check. Failed-order product locks, availability checks, stock decrement, and the paid transition share an exception subtransaction, so a losing unique write rolls its decrement back before returning `payment_id_conflict` (`supabase/migrations/010_catalog_payment_integrity.sql:149-247`). The target-order lock makes repeat confirmation/recapture idempotent.

```
failed order A ── reserve stock ── unique payment write ── wins
failed order B ── reserve stock ── unique payment write ── loses
                         └──── subtransaction rollback ────┘
```

## Verify-first callbacks skip the webhook amount invariant

**Confirmed concern:** a paid row with the same payment ID returns `already_paid = true` at `supabase/migrations/010_catalog_payment_integrity.sql:109-126`; captured amount is checked only afterward at lines 141-148. Browser verification deliberately supplies `NULL`, so if it wins, the later HMAC-verified webhook's amount is ignored. Any local-total/Razorpay discrepancy is therefore callback-order dependent despite the webhook amount being designated authoritative.

Move the non-null amount comparison ahead of the paid return or repeat it inside that branch. Browser `NULL` remains accepted, correct same-ID retries remain idempotent, and every webhook ordering enforces the total.

## Reconciliation responses and unaffected order writers

`markOrderPaid` preserves the new mismatch/conflict reasons (`lib/orders.ts:738-817`). Browser verification returns 409 for semantic reconciliation states and 503 for missing service/local persistence; the webhook acknowledges permanent mismatch/conflict/cancelled/state/stock outcomes but returns 500 for transient persistence or not-found failures (`app/api/razorpay/verify/route.ts:79-104`; `app/api/razorpay/webhook/route.ts:72-96`). Payment-ID mismatch/conflict cannot heal through replay, while a missing row or database outage can.

Migration 010 changes no order-table grants or policies and explicitly retains service-only confirmation execution. Migration 006's service table grants therefore continue to cover payment and Shiprocket writes, while authenticated manual tracking remains under admin RLS. Re-running migration 010 converges its function, ACL, policy, index/drop, and comment changes after a successful first application.
