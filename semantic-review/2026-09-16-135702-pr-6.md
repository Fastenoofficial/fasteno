# Same-project-first production cutover with schema-gated migration

The updated runbook makes the Fasteno.in release a candidate-first, maintenance-gated cutover and prefers promotion inside the domain-owning Vercel project before cross-context transfer. It now deploys the new application before the missing/partial-006 branch, holds maintenance through migrations and synthetic verification, avoids claiming 008/009 are old-app compatible, and ties rollback deployments to reached schema states. Missing live ownership, backup, database fingerprints, provider configuration, and test results correctly remain operational no-go gates rather than source findings. Four confirmed runbook defects and one likely execution gap still prevent approval. **Watch for:** **confirmed** partial migration 006 can satisfy the advertised complete fingerprint; **confirmed** a dummy destination `CRON_SECRET` is authorizing, not inert; **confirmed** custom-domain-only maintenance does not prove Vercel aliases are closed; **likely** the protected deployment has no defined path for Razorpay’s webhook to participate in pre-reopen verification; **confirmed** the undefined source-bundle alternative contradicts the release-SHA invariant.

**Verdict**: NEEDS_CHANGES

## High-level view

The migration state machine now has the intended outer order. A protected candidate precedes every schema-changing branch, missing 006 converges only after writers stop, migrations remain ordered through 010, and the rollback matrix forbids an unknown old build after its compatible boundary.

The 006 decision still rests on an incomplete catalog sample. Presence, selected ACLs, and coarse policy/function metadata do not prove the guest-token constraints, RLS state, PUBLIC and sequence privileges, policy definitions, or security-definer bodies.

The cron intent matches the repository’s two schedules and fail-closed handlers, but one prescribed disablement method has the opposite behavior: setting a different or “non-authorizing” destination `CRON_SECRET` authorizes that destination’s own schedules.

Maintenance is proved only on the custom domain although checkout and newsletter writes accept any host. Source/candidate deployment URLs need the same deny-all proof, and Razorpay needs a tested scoped path through protection for the required webhook checks.

Keeping the domain-owning project is the lower-risk default because it preserves DNS and supports atomic promotion and pinned deployment rollback. It remains conditional on proving ownership, candidate isolation, project-scoped cron/protection behavior, and no traffic movement before maintenance; otherwise the gated transfer path applies.

No live Vercel, Supabase, or provider result was available. The opening NO-GO and mandatory gates correctly leave ownership, backup/PITR, database outputs, anonymous protection, integration results, and rehearsed rollback as launch blockers rather than source defects.

## Migration-006 branch selection can accept a partial security state

The query in `PRODUCTION_CUTOVER_PLAN.md:133-185` lists policy names/commands, table grants for three named roles, function signatures/definer flags/effective execute privileges, one bucket row, and the grace marker. Migration 006 additionally revokes `PUBLIC`, grants `order_number_seq`, creates constrained/indexed guest credentials, enables RLS on two service-only tables, and replaces payment/autocomplete bodies with fixed search-path and privilege semantics (`supabase/migrations/006_security_hardening.sql:11-67`, `95-333`).

A database with a residual `PUBLIC` grant, disabled RLS, missing token constraints/indexes, stale security-definer body, or unsafe policy role/expression can pass the projection. Later anon/auth probes do not prove least privilege, schema constraints, sequence access, or exact function behavior. This is **confirmed**: the runbook can label a partial database “006 complete” and skip convergence. Add exact table/constraint/index/RLS, PUBLIC/role/sequence, policy role/expression, and function definition/configuration checks; alternatively treat any state without a trusted ledger plus exact definition fingerprint as partial and review/re-run 006.

## Destination cron disablement includes an authorizing configuration

The runbook permits a “non-authorizing `CRON_SECRET`” until the source is disabled (`PRODUCTION_CUTOVER_PLAN.md:269-280`). Vercel sends the project’s secret, and both handlers accept that same value; `vercel.json` installs both schedules (`app/api/cron/reap-orders/route.ts:13-30`; `app/api/cron/sync-shipments/route.ts:14-31`; `vercel.json:1-13`). A random destination value is therefore its valid credential.

This is **confirmed**: the documented option can leave both projects authorized. Keep the candidate secret absent, disable its schedules, or add an independent enable gate. If later enabling requires another deployment, pin and reverify its ID/SHA. For same-project promotion, describe the single project’s schedule/deployment transition instead of treating source and destination as independently configurable projects.

## Domain maintenance does not close deployment aliases

The procedure protects and probes the custom domain (`PRODUCTION_CUTOVER_PLAN.md:302-311`), but a fallback leaves the source deployment alive. Checkout and newsletter accept requests without a production-host check and perform service-role writes (`app/api/checkout/route.ts:46-220`; `app/api/newsletter/route.ts:19-96`), so project aliases and immutable deployment URLs remain entrances to production writers.

“Pause ... newsletter/guest/order writers” supplies no mechanism or alias verification. This is **confirmed**: an old alias can write while 006 or 008–010 changes the schema even when `fasteno.in` probes pass. Protect every source/destination alias carrying production credentials, inventory those URLs, and run anonymous negative GET/POST probes against each before migration and after rollback changes.

## Razorpay cannot yet participate in protected verification

Phase 7 requires a low-value payment, captured webhook, replay, and failure behavior; Phase 8 monitors the webhook before protection is removed (`PRODUCTION_CUTOVER_PLAN.md:358-395`). An operator can hold a Vercel bypass cookie, but Razorpay’s server callback cannot do so by implication.

This is **likely**: unless the selected protection supports a route exception or Razorpay can send the exact bypass query/header, the webhook remains blocked and the pre-reopen check cannot run. Rehearse a narrow webhook bypass that does not reopen checkout or anonymous traffic. If unavailable, change the reopening order and retain a separate application maintenance gate for customer writes.

## The source-bundle alternative breaks the release invariant

The runbook mandates a clean checkout of one reviewed commit and downstream release-SHA gates, then permits either that commit or a “controlled immutable source bundle” (`PRODUCTION_CUTOVER_PLAN.md:35-47`, `53-62`). It defines no bundle manifest, content hash, provenance, clean build, deployment identity, or reviewed-diff mapping.

This is **confirmed**: the alternative cannot satisfy the SHA gates but implies declining a commit need not stop deployment. Make the release commit mandatory, or fully define a content-addressed bundle and update every SHA-only gate.
